# CLAUDE.md

CS449/549 term project (Bilkent): vision-based multi-robot sorting on a conveyor belt in RAI (`robotic`), planning with KOMO.
Proposal summary, pipeline and module owners are in `README.md`.

## Commands

```bash
pip install -e ".[dev]"                      # core deps; ".[learning]" adds YOLO / SAM
python scripts/check_env.py                  # must print ENVIRONMENT OK
pytest -q                                    # headless Linux: xvfb-run -a pytest -q
python scripts/run_conveyor.py --view        # conveyor only (or --video out.mp4 headless)
python scripts/run_autonomous.py --view      # autonomous mode (--mode single|fixed|coordinated, --scene clear-and-sort, --detector, --speed, --seed, --video out.mp4)
python scripts/run_command.py "pick a blue box and place it at B" --view   # command mode (no command: type them in)
python scripts/generate_dataset.py --n 2000 --out data/boxes [--preview]
python evaluation/run_experiment.py evaluation/configs/example.json   # one run from a JSON config, metrics appended to results/runs.csv
python evaluation/make_figures.py             # figures and tables of the report from results/*.csv (run the benchmark_*.py scripts first)
```

Headless Linux needs `libglu1-mesa`, `liblapack3`, `xvfb`; every command that renders must run under `xvfb-run -a`.

## Workflow

- One small GitHub issue = one branch = one PR with `Closes #n`, squash-merged into `main`. Issues are numbered `[milestone.step]` and list their dependencies.
- Every PR adds tests; CI (`.github/workflows/ci.yml`) runs `check_env.py` and `pytest` under xvfb.
- PR descriptions state measured numbers and any deviation from the issue text.
- Minimal code, no speculative features. Modules talk only through `src/conveyor_sort/interfaces.py` (`Detection`, `Track`, `Command`, `Assignment`).

## Facts worth knowing

- Physics migration in progress (roadmap #118): `physics/botop.py` starts BotOp in simulation mode (`start_simulation`), `wait_gripper` waits for a gripper command. Needs robotic >= 0.4.3 (0.4.2 does not launch simulated grippers). `gripperDone()` is briefly True right after a command: wait about 0.3 s before polling. BotOp's simulation runs in its own thread and never pauses (no stepping mode): `bot.sync(C, t)` waits `t` of wall-clock time, `get_t()` is the live clock. `botsim/hyperSpeed` speeds it up (real-time factor 1.0 / 5.0 / 9.7 at 1 / 5 / 10), but one sync costs about 40 ms wall time, so above 1 a `World` step is longer than `dt` (mean 0.20 s at 5, 0.38 s at 10). `ry.params_add` does not overwrite a parameter with a value of another type (int 5 after float 1.0 is silently ignored): always pass floats. Same seed, same time: same box positions; runs end at slightly different times.
- Physical conveyor (#89): a rigid body added after BotOp starts crashes `bot.sync` (RAI index range error), so with `physics=True` the conveyor creates `ConveyorConfig.pool` (60) boxes with mass before the start, parked on the ground at y = -2.5 (out of the camera's view; PhysX has its own ground plane at z = 0 and pushes anything below it back up, so parking below the floor does not work). The belt drives the boxes resting on it with `bot.cheat_setFramePose`, front box first (otherwise, with long steps, a box is moved into the one ahead and pushes it away). Boxes held by a gripper (`Conveyor.hold`) or off the belt surface are never written to. Box speed matches the belt within 0.1 %, no lateral drift. `World.close()` must drop every reference to the BotOp (also `conveyor.bot`), or it is destroyed at exit and segfaults.
- Paths on BotOp (#90): with `World(physics=True)`, `follow_path` hands the path to `physics/arms.py` (`ArmReferences`: one timed reference per robot; a new path for one robot is merged with the other's waypoints into the single spline BotOp follows, `bot.move(..., overwrite=True)`, times relative to `overwriteCtrlTime`). The path ends at `world.time + duration` on the simulation clock, so planning time that passed meanwhile is taken from the path. With RAI's default PhysX drive gains the arm lags its reference (2 s pick path: 19 to 30 mm short at its end), so `start_simulation` sets `physx/motorKp` 1e4, `physx/motorKd` 200: 0.2 to 2 mm. These gains are global (fingers too): the friction-grasp squeeze reference was recalibrated for them.
- The arm follows BotOp's spline 0.1 s late (`arms.LATENCY`; joint error during a pick 74 to 82 mrad mean against the reference, 4 to 10 against the reference shifted by 0.1 s): every reference is sent 0.1 s early. Without it a moving pick at 0.2 m/s arrived 25 mm behind and 20 mm above the box. Re-planning one arm briefly disturbs the other (28 mrad against its reference, 8 to 18 without): known limitation.
- Physical pick (#91, `PickPlaceTask(..., pick_only=True)` on the physics backend): with active fingers q is `[l arm 0..6, l finger 7, r arm 8..14, r finger 15]`; use `scene.arm_joints(C, robot_id)`, never fixed slices. KOMO's `qItself` over all joints has 18 entries then (mimic joints): `plan_home` targets the arm joints by name. The planners optimize the arm joints only (`pick._komo` selects them for KOMO, `_solve` re-inserts the finger values; an equality constraint on the fingers instead made about 1 in 10 lifts infeasible); `ArmReferences` replaces a path's finger column by the robot's finger target, so the squeeze stays on during the lift. While squeezing, plan in `grasping.planning_view` (open fingers, box attached in C only; the squeezed fingers penetrate the box and KOMO would report a collision). At pick time `Conveyor.hold(box)` stops the belt drive (#89's 6 cm gripper-proximity rule stopped the box while the gripper was still descending). Outcomes: "grasp" (nothing between the fingers), "slip" (box did not rise with the gripper).
- Physical place (#92, `PickPlaceTask` on the physics backend without `pick_only`): `plan_place` in `planning_view` lowers the box to its resting height (`drop` / `clearance` higher), the fingers open, `Conveyor.unhold`, then retreat 10 cm up and home. The regions have no collision geometry: the box rests on the table. `result.place_error` / `result.tilt` are measured after home; "release" if the box is not inside the region or tilted >= 10° (`MAX_TILT`). Measured on a stopped belt (5 robot-region pairs) and at 0.2 m/s: error 0.2 to 1.9 mm, tilt below 0.04°, also when dropped from 2 cm.
- Regions with several boxes (#93, physics backend): `regions.SLOTS`, 2 x 3 slots per region (10 cm apart in x, 7 cm in y: the fingers close along x and the place keeps that orientation, so with 7 cm in x the place next to a box could not be planned); `PickPlaceTask` places into the first free slot whose place can be planned (`free_slots`, `plan_place(..., offset=)`), `result.place_error` is measured to the slot centre, a full region fails with "full" before the arm moves. Boxes into one region one after another: region A 6 of 6 then "full", region B 5 or 6, bin 5 (the last free slot sometimes cannot be planned); error 0.2 to 4 mm; neighbours are nudged by up to 3 cm (x and y each within the 3 cm slot tolerance). The sorting loop still removes the previous box of a region (kinematic backend; removal goes in M12). On physics a full region is emptied when a task for it starts (`sorting.collect_if_full`, also in `CommandMode`; only one robot works in a region at a time, so no arm is above it; counted in `SortingStats.regions_emptied`, #142): before, long runs ended in "full" failures (#107: about 40 per configuration).
- Two arms under physics (#95): BotOp exposes no PhysX contact list; `physics/contacts.arm_proximity` checks the two arms' collision shapes at the simulated poses after every step (`run_robots` logs `min_arm_distance`, `arm_contacts`). Coordinated 60 s runs at 0.1 and 0.2 m/s: no contact (closest 11.5 cm), no two shared-area tasks at once. Needed on the way: `grasping.planning_view` opens the fingers of *both* robots in C (the other arm's squeezed fingers penetrate its box; with that arm static, every plan was infeasible while it held a box) and leaves out boxes that penetrate a non-robot object by more than 3 mm; after a failure past the grasp the physical task lets go and goes home (retreat planned with the released box ignored, `grasping.ignoring`) instead of stopping where it is; the belt jams a box behind a held box (`Conveyor.step`) and takes out a box whose centre passes the belt end (some hung on the edge and were pushed into). Before these: 1 of 7 sorted in a coordinated run; after: 37 of 37 (6 runs).
- Command mode on physics (#109, 160 commands): 92 / 98 % correct at 0.1 / 0.2 m/s (kinematic: 100 %), 90 / 75 % when every box has a gray box 8 cm in front of it, about 20 s per command; failures mostly "grasp" (9 of 10 at 0.2 m/s with blocked boxes). `command.selection` does not check blockers (unlike `allocate`): a blocked box is grasped along the belt anyway, the 2 cm gap is usually enough on a slow belt (#99: a 3 cm gap already fails along a belt at 0.1 m/s in the scripted case). The physics box pool reuses boxes taken out (fell off the belt end) once all `ConveyorConfig.pool` boxes have been spawned.
- Recovery (#105): the place motion stops as soon as the carried box is more than 4 cm from the gripper ("drop"); after "slip" / "drop" `result.dropped_on` says where the box came to rest (belt, table, box, region, floor). The sorting loop tries a box again after "grasp", "slip", "lift", "drop" (`RETRY_STAGES`), 0.5 s later, up to `MAX_ATTEMPTS` (3); `SortingStats.failures` / `drops` count them. A held box is not detected (not on the belt), so its track is dropped after 2 s and a new one starts when it falls back: the new track inherits the attempt count if it appears where the failed box is expected (pick position moved on by the belt, `INHERIT_X` / `INHERIT_Y`), else a box was tried 4 times. Physics backend: tasks still running at the end of a run are finished (`FINISH_TIMEOUT`), so no arm keeps a box. Friction 0.05: the squeeze shoots the box off the table (floor); 0.1 / 0.15: slips during the lift, lands on the belt; 0.2: held.
- Disturbed boxes (#104): the tracker takes a detection more than `tracker.JUMP` (1.5 cm) from its prediction as a displaced box (history shifted, velocity kept; Kalman: beyond 1.5 cm plus 3 standard deviations, so a new track can still learn its velocity); beyond the 5 cm gate a new track starts. While the arm approaches, `run_robots` / `CommandMode` call `PickPlaceTask.observe(tracks)`: a box predicted more than 1.5 cm from where the pick aims is aimed at again (`_plan_pick` from the arm's current state, the target box ignored as an obstacle: the fingers are already around it), a box not seen for 1.2 s ends the attempt with "lost". Box pushed 3 cm along the belt early in the approach: gripper 0.6 to 3.3 mm from the box at the grasp with re-planning, 13.8 to 28.8 mm (or a failed first grasp) without. Both were still sorted: until the grasp the belt sets the boxes' poses, so a finger landing on a box is pushed out of it and the squeeze centres the box (a real belt would not forgive that).
- Arm motions checked against each other (#141): each arm is planned with the other one static, which is only safe if the other one does not move meanwhile; the shared-area rule does not see recovery or re-planned motions (#107: contacts in 6 of 117 runs). Before every stage the physical task samples its path and the other arm's current reference at the same times (`ArmReferences.clearance`, `moving_until`); if the other arm moves and they come closer than 2 cm (`pick_place.CLEARANCE`), the stage waits until that motion has ended (at most `MAX_WAIT` 15 s) and plans again; a pick (timing fixed by the moving box) is given up as "pick" and retried 0.5 s later. Counted in `PickPlaceTask.waits` / `SortingStats.arm_waits`. Test: Robot 1 picks next to the moving Robot 2: without the check 7.9 cm penetration, with it no contact.
- Manipulation benchmark on physics (#107, `benchmark_manipulation.py --physics --jobs 4`, 117 runs, about 2.5 h; results/manipulation_physics.csv, table in tables.md): sorted 30.9 / 52.4 / 54.1 % (single / fixed / coordinated) against 40.6 / 72.2 / 72.8 % kinematic, throughput 2.5 / 4.4 / 4.5 boxes per min against 3.3 / 5.9 / 6.0; a physical pick and place takes longer (squeeze, settling, recovery). Failed attempts: 5 to 13 per 100 boxes, mostly drops in transport (56 in all, landing on belt 21, table 20, region 15, floor 1), grasp failures (19), and in long runs "full" regions (no box is ever taken out on physics: a region holds 6, the bin about 5) and places next to boxes not plannable. Arm contacts in 6 of 117 runs (up to 5.5 cm), not reproducible run to run; one traced case followed a drop recovery (the retreat and home paths are not covered by the shared-area rule). Planning time per pick and place 1.5 s (0.15 s kinematic: the physical task also plans the retreat, re-plans, and 4 runs shared the CPU).
- Friction grasp (works, #87; `physics/friction_grasp.py`, `scripts/spikes/friction_grasp.py`): make the finger joints active (`activate_fingers(C)`: `C.selectJoints(...)`, q grows from 14 to 16; `getJointNames` also lists the mimic `finger_joint2`, which is not in q) and drive them with the arm PD controller through the path / `moveTo`: open 0.04, squeeze reference 0.022 (with the drive gains of #90). The fingers touch a 6 cm box at 0.030 and settle near 0.0237; on nothing they settle near 0.0222, so `finger_q > 0.023` means holding (small margin: 0.7 mm each side). PhysX friction 1.0 (`physx/defaultFriction`, set before BotOp starts). Holds 0.05 to 1.0 kg, rotated boxes, both robots; with friction 0.05 the box stays on the table (proof that friction holds it).
- Do not use `gripperClose` for grasping: it stops about 5 mm before the object and never squeezes (no normal force, nothing held). Do not use `gripperCloseGrasp`: it lifts the object without closing the fingers (simulator shortcut, effectively an attachment).
- After `start_simulation` the synced box pose can still be the spawn pose for a moment: read object poses after the first motion, not right after the start.
- Kinematic backend (`World()` default): grasp and release are kinematic, the box is attached to the gripper / the region. The physics backend grasps by friction (#91) and places physically (#92). Since #96 the demo scripts (`run_conveyor`, `run_autonomous`, `run_command`) run on physics (real time: a 60 s run takes about 70 s), with the detector on BotOp images (`get_detector`) and the video from a `CameraView` of the synced state (BotOp's images are only 2 per s). On physics the sorting loop and command mode do not empty a region before placing (slots, #93), `allocation.max_track_gap` is 0.7 s instead of 0.2 s (BotOp's image interval), and clear-and-sort is off. Physics scenario tests: `tests/test_loops_physics.py` (single robot 5 of 5 in 65 s instead of 60 s: a physical pick and place takes about 2 s longer).
- Stationary pick-and-place sequence: `plan_pick`, `grasp`, `plan_lift`, `plan_place`, `release`, `plan_lift` (retreat up, otherwise the fingers hit the box), `plan_home`; see `tests/test_place.py`.
- `plan_moving_pick` path must be executed in exactly `pick_time - now` seconds; the planner treats the box as static at its current position for collision checks.
- Never `delFrame` while planning is in use: RAI's collision engine keeps stale geometry (wrong KOMO results or a crash). `Conveyor.remove` parks boxes below the floor instead. Only `perception/dataset.py` deletes frames (no planning there).
- A box can be reachable (IK) but not liftable: at the edge of the workspace, and also from some grasp poses well inside it (far side of the belt at slow speed). `reach.can_pick` checks points at lift height 10 cm up- and downstream; `PickPlaceTask` plans the lift from the pose the pick ends in before it starts moving and reports a "pick" failure otherwise (the sorting loop retries 0.5 s later). Before that check a failed lift left the arm holding the box for the rest of the run.
- KOMO optimizes the joints of both arms unless `planning.pick.own_arm_only(C)` is active, but only the planning robot's joints are executed: a plan that moved the other arm out of the way (by 0.14 rad, reported feasible) went 14 cm into it (#141). On physics, `planning_view` plans one arm only while the other stands still; while it moves, `ArmReferences.clearance` checks the plan against its real motion (a static-arm plan would refuse paths the other arm is about to clear, e.g. clear-and-sort). The kinematic backend still plans both arms. Two arms working close together collide. Priority rule: the shared area (belt x in (-0.3, 0.4) and region B) is used by one robot at a time, for its whole pick-and-place; the other robot may only take boxes outside of it. `SortingStats.conflicts` / `waiting_time` log it. The rule is by pick position: a moving pick follows the box during its last 20 %, so a Robot 2 pick at x = 0.4 at 0.2 m/s brings its gripper to x = 0.3 (measured under physics while Robot 1 worked at -0.26; the arms stayed more than 11 cm apart). Counting that stretch as shared cost fixed roles 1 of 5 boxes (#95), so it is not counted. Robot 2 picks only at x >= 0.4 (`allocation.PICK_X`): nearer to its reach limit (-0.2) the lift fails and the arm is left holding the box.
- Layout (#154): the robots stand on opposite sides of the belt at its middle (Robot 1 at (0, -0.3), Robot 2 at (0, 0.7), both 0.5 m from the belt centre line), each facing it. Every approach from home swings over the middle of the belt and the arms reach towards each other, so only one arm may be over the belt at a time (`PickPlaceTask.at_belt`: from the start until the lift; the other arm may place on its own side meanwhile). Rules by pick position failed (a band around the overlap of the pick zones, or 0.3 m from the other robot's zone: the hands met over the belt). `SortingStats.conflicts` / `waiting_time` log it. Pick zones `allocation.PICK_X`: Robot 1 x <= 0.15, Robot 2 x >= -0.15. Each robot's regions lie on its side, away from the other robot's zone (A, B, C upstream, the bin downstream); with region B downstream, Robot 1 carried boxes through Robot 2's zone.
- A pick plan can fail where IK says reachable (box just entering a robot's workspace): the sorting loop retries that track 0.5 s later instead of giving up.
- The fingers close along the belt (box faces at -x / +x): a neighbour closer than 11 cm in front of or behind a box in the same lane is hit (the planner does not see it: it checks collisions with the boxes where they are at planning time). `allocate` skips such boxes. `plan_moving_pick(across_belt=True)` grasps on the -y / +y faces instead.
- Clear-and-sort is off on the physics backend (`plan_clear_and_sort` returns None): Robot 2 stays at the belt 2.2 s longer (squeeze, settling), and with the kinematic timing it lifted into Robot 1's path (7 cm arm penetration); with 2.2 or 3.2 s more delay Robot 1 could not plan its pick past Robot 2's arm. #101 / #102.
- Clear-and-sort (kinematic) up to 0.08 m/s, gray box on either half of the belt, in front or behind; Robot 1 grasps `CLEAR_DELAY` 4 s after Robot 2 (with 3 s the arms, reaching to the same spot from opposite sides, touched in 8 of 9 scenarios). On physics clearing runs as a job, one arm at a time (#101).
- A region holds one box: the sorting loop removes the previous box before the next one is placed there.
